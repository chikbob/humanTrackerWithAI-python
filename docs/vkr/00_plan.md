# План и аналитическая основа ВКР

## 1. Глубокий анализ проекта

### 1.1. Краткое описание проекта

Проект представляет собой веб-систему мониторинга проходной зоны предприятия с обработкой видеопотоков в реальном времени. Текущая реализация построена как `Streamlit`-приложение с отдельным фоновым `worker`, который получает кадры из активных источников, запускает детекцию и трекинг людей на `YOLOv8`, интерпретирует ROI как контролируемую входную зону и сохраняет события в `SQLite`. Ключевые точки входа системы расположены в файлах `app.py`, `run_worker.py`, `video/worker.py`.

### 1.2. Тема и предметная область

Фактическая предметная область проекта: контроль и анализ прохода сотрудников через входную зону предприятия на основе видеонаблюдения.

Проект не является универсальной системой анализа любых объектов и не реализует полноценную систему контроля и управления доступом. По структуре кода и пользовательским сценариям он соответствует интеллектуальной системе видеомониторинга проходной, в которой:

- объектом наблюдения выступает человек в кадре;
- зоной интереса является входная зона или точка доступа;
- предметными событиями являются появление человека у входа, вход в зону, выход из зоны, длительное присутствие, повторная попытка входа, недоступность камеры и восстановление соединения;
- организационный контур поддерживается справочником сотрудников, ручной привязкой событий к сотрудникам и аналитикой по накопленным данным.

### 1.3. Карта архитектуры

Фактическая архитектура проекта монолитная, но логически разделена на несколько слоев.

- UI-слой: каталог `ui/`, маршрутизация экранов выполняется в `app.py`.
- Слой компьютерного зрения для интерактивных режимов: `core/detection.py`.
- Production video ingest и worker: `video/worker.py`, `video/pipeline.py`, `video/runtime.py`.
- Предметная логика событий: `services/events.py`.
- Управление состоянием сеансов и логирование кадров: `services/state.py`.
- Работа со справочником сотрудников и синхронизацией: `services/employee_repository.py`, `services/employee_sync.py`.
- Заготовка под идентификацию личности: `services/identity_service.py`.
- Слой хранения данных: `db/repository.py`.
- Аналитические агрегации: `analytics/access.py`.
- Конфигурация: `config/app_config.py`, `config/rtc_config.py`.
- Развертывание: `Dockerfile`, `docker-compose.yml`.

Production-сценарий работы системы имеет следующий вид:

1. Фоновый `worker` читает активные серверные источники из таблицы `video_sources`.
2. Для каждого источника выполняется детекция и трекинг через `YOLOv8` и `ByteTrack`.
3. ROI интерпретируется как входная зона предприятия.
4. Сырые и предметные события сохраняются раздельно.
5. `worker` обновляет `worker_status` и сохраняет последний snapshot источника.
6. UI читает данные из БД и runtime-файлов и отображает дашборд, онлайн-мониторинг, журнал и аналитику.

### 1.7. Фактическая модель хранения данных

Реально используемые таблицы:

- `employees` - карточки сотрудников, ФИО, табельный номер, подразделение, должность, статус, даты, внешний источник;
- `access_points` - точки прохода;
- `video_sources` - источники видеоданных;
- `worker_status` - heartbeat, статус подключения, FPS, ошибки, путь к snapshot;
- `events` - единый журнал всех событий;
- `detection_events` - сырой слой CV-событий;
- `access_logs` - предметный журнал проходной;
- `sessions` - сеансы мониторинга;
- `frames` - сведения о кадрах в foreground-режимах;
- `system_settings` - системные параметры;
- `employee_sync_state` - состояние синхронизации справочника.

Состояние текущей БД `monitoring.db` на момент анализа:

Это подтверждает, что текущая реализация ориентирована прежде всего на событийный контур проходной и на контроль состояния источников, а не на длительное хранение покадровой истории.

### 1.8. Ограничения и не полностью реализованные возможности

- автоматическая идентификация сотрудника по лицу не реализована; в `services/identity_service.py` присутствуют только безопасные заглушки и статусы деградации;
- аутентификация, авторизация и ролевая модель пользователей в системе отсутствуют;
- ROI в worker сейчас задается фиксированно в коде и не настраивается из интерфейса индивидуально для каждого источника;
- production-пайплайн worker обрабатывает только класс `person`; исторические элементы, связанные с животными, не являются предметным ядром текущей версии;
- `ui/analytics.py` выглядит как альтернативный или устаревший модуль и не подключен к актуальной маршрутизации;
- таблица `frames` предусмотрена, но в текущем демонстрационном заполнении не используется;
- отдельного REST API не реализовано; система построена как Streamlit-монолит с фоновым процессом;
- часть тестов зависит от Python 3.11+ и наличия CV-зависимостей.
