# Веб-система мониторинга прохода сотрудников на предприятии

Проект соответствует теме ВКР:
**«Разработка веб-системы мониторинга и интеллектуального анализа объектов в реальном времени с использованием нейросетевых моделей»**.

Прикладной акцент текущей реализации:
**мониторинг прохода сотрудников на предприятии через входную зону и точки доступа**.

Система представляет собой веб-приложение на `Streamlit` с выделенным фоновым сервисом обработки видеопотока. Интерфейс предназначен для оперативного наблюдения за входной зоной предприятия, контроля состояния источников видео, ведения журнала событий проходной, работы со списком сотрудников и базовой аналитики по событиям доступа.

## Что реализовано

- корпоративный многосекционный UI:
  - `Дашборд`
  - `Онлайн-мониторинг`
  - `Сотрудники`
  - `Журнал событий`
  - `Аналитика`
  - `Источники видео`
  - `Настройки системы`
- фоновый `worker` для 24/7 обработки RTSP/IP/USB/HLS-источников без постоянно открытой страницы пользователя;
- нейросетевая детекция и трекинг людей на базе `YOLOv8`;
- интерпретация ROI как входной зоны предприятия;
- журналирование сырых событий детекции и предметных событий проходной;
- базовый справочник сотрудников;
- управление источниками видеоданных;
- хранение данных и настроек в `SQLite`.

## Предметная логика

В текущей версии система формирует и сохраняет события:

- `person_detected_near_entry`
- `person_entered_entry_zone`
- `person_left_entry_zone`
- `prolonged_presence_near_entry`
- `unknown_person_detected`
- `repeated_entry_attempt`
- `stream_offline`
- `camera_reconnected`

Сырые события детекции и предметно-ориентированные события разделены логически и сохраняются раздельно, чтобы проект можно было развивать в сторону СКУД и идентификации сотрудников без переделки основной архитектуры.

## Архитектура

Проект разделен на несколько слоев:

- `app.py` — основной веб-интерфейс и маршрутизация экранов;
- `video/` — серверный ingest и фоновый worker для постоянной обработки источников видео;
- `core/` — нейросетевая детекция, трекинг и обработка ROI;
- `services/` — генерация событий предметной области, состояние сессий, подготовка к идентификации;
- `db/` — слой работы с `SQLite`;
- `ui/` — отдельные экраны и элементы интерфейса;
- `analytics/` — агрегации для dashboard и аналитики;
- `config/` — системные параметры по умолчанию;
- `models/` — прикладные сущности.

### Production path

Основной сценарий работы теперь такой:

1. Фоновый `worker` читает активные серверные источники видео.
2. `worker` выполняет детекцию и трекинг людей.
3. Система формирует события доступа и обновляет `worker_status`.
4. `worker` сохраняет последний annotated snapshot источника.
5. Streamlit UI читает данные из БД и runtime snapshot-файлов.
6. Пользователь видит dashboard, журнал и аналитику независимо от жизненного цикла видеопотока.

### Demo / fallback path

Браузерная камера, локальная камера и загрузка файлов оставлены как вспомогательные режимы для демонстрации и локальной отладки. Они не считаются основным production-сценарием.

## Запуск локально

### 1. Установка зависимостей

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Запуск UI

```bash
streamlit run app.py
```

### 3. Запуск фонового worker

В отдельном терминале:

```bash
python run_worker.py
```

Проверочный одноразовый цикл:

```bash
python run_worker.py --once
```

## Production mode на VPS / сервере

Для production-режима рекомендуется использовать:

- `RTSP/IP camera`;
- `USB camera`, подключенную к серверу;
- `HLS/HTTP stream`;
- отдельный процесс `worker`;
- `Docker` или `docker compose`;
- постоянное хранение `SQLite` и runtime snapshot-файлов на volume.

### Переменные окружения

- `MONITORING_DB_PATH` — путь к файлу БД.

Пример:

```bash
export MONITORING_DB_PATH=/opt/employee-access/data/monitoring.db
```

## Подключение RTSP-камеры

1. Откройте раздел `Источники видео`.
2. Добавьте новый источник типа `RTSP/IP camera`.
3. Укажите строку подключения, например:

```text
rtsp://user:password@192.168.1.50:554/stream1
```

4. Нажмите `Тест подключения`.
5. Активируйте источник.
6. Убедитесь, что `worker` запущен.
7. Перейдите на `Дашборд` или `Онлайн-мониторинг`.

### Browser live в отдельном окне

Для отдельного окна browser live monitoring нужен runtime с `Python 3.11` и установленным `streamlit-webrtc`.
Практически это означает:

- локально лучше запускать новый `venv` на `Python 3.11`;
- на VPS и в Docker использовать базовый образ `python:3.11`;
- для удаленного сервера нужен `HTTPS`;
- для стабильного WebRTC через интернет желательно настроить `TURN`.

Используемые переменные окружения:

- `STUN_URLS`
- `TURN_URLS`
- `TURN_USERNAME`
- `TURN_PASSWORD`

Пример `.env`:

```bash
cp .env.example .env
```

Если проект запускается через `docker compose`, то `coturn` поднимается вместе с приложением и значения по умолчанию уже прокинуты в `ui` и `worker`.

### Реально рабочий browser live для production

Рекомендуемый сценарий:

1. Использовать `Python 3.11`.
2. Поднять проект через `docker compose`.
3. Завести `HTTPS` через reverse proxy.
4. Использовать встроенный `coturn` или внешний TURN-сервер.
5. Открывать `?view=live-window&source=browser_camera` в отдельном окне.

Это самый практичный путь для Streamlit-приложения, если нужно непрерывное браузерное live-наблюдение. Без `TURN` browser live на удаленном сервере может не устанавливать медиасессию. Источник: https://github.com/whitphx/streamlit-webrtc

## Как работает 24/7 режим

- `worker` циклически опрашивает активные источники из таблицы `video_sources`;
- при потере потока обновляет статус и создает событие `stream_offline`;
- при восстановлении соединения создает событие `camera_reconnected`;
- сохраняет heartbeat, FPS, ошибки и путь к последнему snapshot в таблице `worker_status`;
- Streamlit UI читает уже сохраненные результаты и не является владельцем основного видеопотока.

## Параметры, влияющие на производительность

- `frame_skip` — уменьшает число кадров, проходящих через инференс;
- `inference_size` — определяет размер кадра для нейросетевой модели;
- `confidence_threshold` — влияет на объем детекций и нагрузку последующей логики;
- `reconnect_interval` — интервал повторной попытки подключения к источнику;
- `source_timeout` — ориентир для контроля актуальности видеопотока;
- `event_cooldown` — окно для подавления слишком частых доменных событий.

## Сценарий демонстрации

1. Запустить `streamlit run app.py`.
2. Запустить `python run_worker.py` или использовать fallback demo-режим.
3. В разделе `Источники видео` добавить production-источник либо включить `Демо / fallback режим`.
4. Перейти на `Онлайн-мониторинг` и показать обнаружение человека во входной зоне.
5. Перейти в `Журнал событий` и показать фиксацию событий проходной.
6. Перейти в `Аналитику` и продемонстрировать агрегированные показатели.
7. При необходимости открыть раздел `Сотрудники` и показать справочник предприятия.

## Ограничения текущей версии

- полноценная биометрическая идентификация сотрудников пока не реализована и подготовлена только архитектурно;
- `SQLite` подходит для ВКР, демо и прототипа, но для крупного промышленного deployment целесообразно перейти на серверную СУБД;
- snapshot в UI отражает последнее состояние источника и не всегда является отдельным архивным кадром каждого события;
- текущая интерпретация `repeated_entry_attempt` и `unknown_person_detected` реализована как безопасная прикладная эвристика.
